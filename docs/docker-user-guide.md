# GPUサーバーでDockerを使う

Dockerは、研究に必要なPython・ライブラリなどをイメージにまとめ、そのイメージからコンテナを起動して実行環境を用意する仕組みです。**許可されたGPUサーバーへSSH接続してから、そのサーバー上でDockerを操作します。** `-lan`・`-campus`・`-ssm` のどの経路でも、接続後の操作は共通です。

## 1. 利用できる環境と権限

対象はRTX-A6000x2、AIsawa（RTX 6000 Ada搭載機）、RTX-6000ada、RTX4090、RTX5090の5台です。FreeIPAの `labusers` または `go2poc` に所属する利用者へ、共通設定でsudoなしのDocker利用権限を付与します。利用できるサーバー・グループ・期間は管理者の通知に従ってください。SSH接続できることだけではDockerの利用許可を意味しません。

管理者がDockerの操作窓口であるソケットにグループ権限を設定します。利用者が自分で `docker` グループへ追加したり、ソケットの権限を変更したりする必要はありません。

**同じGPUサーバーのDocker環境は他の利用者と共有しています。** Docker実行権限は実質的にroot相当です。FreeIPAアカウントが個別でも、Docker上で他人のコンテナが自動的に非表示・操作不能になる構成ではありません。他人のコンテナ・イメージ・ボリューム・ネットワークや監視用コンテナを停止・削除・変更しないでください。

## 2. 最初の利用確認

自分のPCから、許可されたGPUへ接続します。以下はRTX5090への学内接続の例です。

```bash
ssh rtx5090-campus
```

接続先の端末で次を実行します。

```bash
hostname -f
whoami
id
nvidia-smi
docker version
docker ps
```

| 確認項目 | 期待する結果 |
| --- | --- |
| 接続先・本人確認 | 許可されたGPUのホスト名、本人のFreeIPAユーザー名、承認されたグループ |
| ホストのGPU認識 | `nvidia-smi` に対象GPUが表示される |
| Dockerへの接続 | `docker version` にClientとServerの情報が表示される |
| コンテナ一覧の取得 | `docker ps` が権限エラーなく終了する。一覧が空でも正常 |

ここまででは、使用予定のコンテナ内でGPUやPyTorchが動くことまでは確認できません。`permission denied` やDockerデーモンへの接続エラーが出る場合は、接続先・発生時刻・エラーを管理者へ伝えてください。sudoや権限変更で回避せず、管理者に登録・サービス状態の確認を依頼します。

## 3. 研究用コンテナを始める前に

管理者またはプロジェクト担当者と、次の内容を確認してからコンテナを起動します。

| 決めること | 確認内容 |
| --- | --- |
| 実行環境 | 使用するイメージ名とタグ、Python・CUDA・PyTorch等のバージョン、起動コマンド |
| GPUと期間 | 利用するGPU番号・枚数・時間。GPU使用率が0%でも予約・利用許可を確認する |
| コンテナ名 | 自分のユーザー名と研究名など、他人のものと区別できる名前 |
| 保存先 | ホスト側の作業ディレクトリ、許可されたNFS領域、コンテナへのマウント先 |
| ファイルの権限 | コンテナの実行UID/GIDと、共同作業に必要なグループ権限 |
| ポート | Jupyter等を使う場合のポート番号とアクセス方法 |

参照元のDocker利用手順では、全利用者向けの統一済み学習イメージや一律の起動コマンドは指定されていません。プロジェクトで確認したものを使用してください。GPUを使う起動指定も対象ホストの設定に合わせます。参照元にはRTX-A6000x2のNVIDIA runtime/CDIに関する注意があるため、他のサーバーの起動指定をそのまま流用せず、動作確認済みの指定を担当者から受け取ってください。

研究を始める前に、使用するコンテナ内でのGPU認識と、研究コードが使うフレームワークからのGPU利用を確認します。ホスト側の `nvidia-smi` の成功だけで学習環境の確認完了とはしません。

## 4. データ保存と共同利用

コード・データ・学習結果は、コンテナを削除した後も残るよう、許可されたホスト側ディレクトリをマウントして保存します。コンテナ内部だけに置いたファイルは、コンテナを削除すると失われます。保存先とマウントの設定はプロジェクトの起動手順で確認してください。

GPUサーバー上の共有領域は `/mnt/nfs-shared/...` です。`labusers` には `/mnt/nfs-shared/labusers`、承認された `go2poc` 利用者には `/mnt/nfs-shared/go2poc` を使用する構成です。本人に通知された領域だけを利用してください。Dockerイメージやコンテナそのものが、FreeIPAやNFSによって全GPUへ自動的に共有されるわけではありません。

NFSは `root_squash` を使うため、コンテナ内のrootで実行しても共有領域へ自由に書き込めるわけではありません。本人のUID/GID・必要なグループと保存先の権限を合わせ、研究を始める前に小さな試験ファイルの作成・読出し・所有者を確認します。問題があれば権限を広げず、担当者に実行ユーザーとマウント設定の確認を依頼してください。詳しくは[共有領域の確認手順](remote-access-user-guide.md#43-nfs共有を使う)を参照してください。

コンテナの起動前にGPU・ポート・保存先・利用期間を関係者と調整し、終了時は自分が作成した対象だけを整理します。サーバー全体の一括削除や `docker system prune` は利用者の後片付けとして実行しません。OS・GPUドライバー・Dockerサービスの変更は管理者が行います。

## 5. ジョブ情報の登録

参照元には、GPU監視画面へ研究名・ジョブ名などを申告する `lab-gpu-job` があります。全利用者への配置済みを前提とせず、利用する場合は管理者から導入・実行手順を受け取ってください。登録はGPUの予約や実行権限の付与ではありません。

登録する研究名・モデル名などは監視画面で共有される情報です。参照元ではAWSの監視画面を一般公開する運用が記載されているため、公開可能な名称だけを使用し、未公開の研究情報や認証情報を含めないでください。Dockerの申告者情報は、起動者を監査で証明するものではありません。
